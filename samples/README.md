## `results/`: real CI result files

Every file here is a JUnit XML report that a GitHub Actions run of one of my public test
automation repositories produced. Nothing in them is invented; they were cleaned with
[`tools/sanitize_junit.py`](../tools/sanitize_junit.py) before committing.

| Folder | Producer | Repository / CI job | Runs |
|---|---|---|---|
| `pytest-notes-api` | pytest 9 (`--junitxml`) | [python-pytest-framework](https://github.com/niranjankagri/python-pytest-framework), API job | 7 (13-19 Oct 2026) |
| `pytest-notes-ui-chromium` | pytest 9 + Playwright for Python | python-pytest-framework, UI job (Chromium) | 7 |
| `robot-saucedemo-chrome` | Robot Framework 7 (`--xunit`) | [robot-framework-automation](https://github.com/niranjankagri/robot-framework-automation), Chrome job | 11 (9-19 Oct) |
| `testng-enterprise-regression-firefox` | Maven Surefire 3.5 + TestNG 7 (Selenium) | [enterprise-test-automation-framework](https://github.com/niranjankagri/enterprise-test-automation-framework), nightly regression on Firefox | 13 (7-19 Oct) |
| `playwright-toolshop-firefox` | Playwright Test 1.64 (`merge-reports --reporter junit`) | [playwright-typescript-framework](https://github.com/niranjankagri/playwright-typescript-framework), Firefox job | 5 attempts of 3 runs |

**File names:** `<date>_<commit>_<GitHub run id>.xml`; Playwright files add `-attempt<N>`
because one run was re-run twice. The commit is the build that was tested.

**What happened in these runs (all real):**

- `testng-enterprise-regression-firefox/2026-10-13_...`: one failure, a Selenium
  `TimeoutException` in `CustomerManagementTest.adminEditsACustomer` (the login page did not
  become ready on Firefox within 10 s). The next nightly passed without a code change.
- `playwright-toolshop-firefox/2026-10-19_..._39229363499`: attempt 1 had one failed checkout
  test, attempt 2 had two errors (the public demo site timed out on API calls), attempt 3 passed.
  Same commit throughout: an outage of the site under test, not a code change.
- Everything else passed.

**What the sanitiser changed:**

- removed test logs (`<system-out>`, `<system-err>`), `hostname` attributes, XML comments and
  properties outside an allow-list (Surefire writes every JVM property: class paths, home
  directories, user names);
- replaced local file paths in failure messages with `<local path>`: `playwright merge-reports`
  writes the attachment paths of the machine that merged the reports into the failure text.
  (The first published version of the two failed Playwright attempts still contained such a
  path; `tests/integration/test_repository_hygiene.py` found it and now guards every file);
- added run context as suite properties: `framework`, `browser`, `environment=ci`,
  `platform=linux` and `build=<commit>`, taken from the CI job definition and run page;
- added a suite `timestamp` with the CI run's start time where the producer wrote none
  (Surefire), and replaced the merge time that `playwright merge-reports` writes with the
  start time of the run attempt.

Test names, outcomes, durations and failure messages are unchanged. `tests/integration/test_real_samples.py`
checks every file against the totals the producer itself wrote into it.

**Not included:** a Playwright Chromium set (artifacts were too slow to download completely in
the session that built these samples). Cypress and Allure results are in `formats/` below.

## `formats/`: other result formats (real CI output)

Kept apart from `results/` so the demo, the catalog and the gates keep working on the JUnit
set they were written for. Cleaned with [`tools/sanitize_reports.py`](../tools/sanitize_reports.py)
(and `sanitize_junit.py` for the JUnit copies).

| Folder | Producer | Repository / CI job | Runs |
|---|---|---|---|
| `cypress-taskboard-api` | Cypress 16.2 + cypress-mochawesome-reporter 5 (HTML report, JSON taken from its `data-raw`) | [cypress-typescript-framework](https://github.com/niranjankagri/cypress-typescript-framework), API job (default browser Electron) | 4 (16-19 Oct), 31 tests each |
| `cypress-taskboard-ui-chrome` | same | same repository, UI job on Chrome | 4 (16-19 Oct), 33 tests each |
| `allure-enterprise-api` | Allure 2 TestNG adapter (`allure-results` folder, one folder per run) | [enterprise-test-automation-framework](https://github.com/niranjankagri/enterprise-test-automation-framework), API job | 5 (6-19 Oct), 57 tests each |
| `allure-enterprise-nightly-full` | Allure 2 TestNG adapter | enterprise-test-automation-framework, nightly job *Full suite (Chrome)*, run 39385969773 (20 Oct) | 1, with 169 executions (its CI log: "169 passed"), incl. 4 invocations of one method (`invocationCount`) |
| `junit-enterprise-api` | Maven Surefire, the same CI job and run as `allure-enterprise-api` | same | 5 |

One run per day was kept (the latest of that day). All of these runs passed.

**Why the JUnit copies:** the API job writes both formats in the same run, so the two can be
compared test by test. `tests/integration/test_format_samples.py` does that: same number of
tests, identical keys for plain test methods, data-driven rows matched by their parameter
values (the two reporters order and name parameters differently), same outcomes, and
durations within the measured difference of the two reporters (median about 0.08 s).

**What the sanitiser changed:** mochawesome: removed each test's source (`code`) and
`context` (embedded screenshots), masked local paths in failures, recorded the run context
(`qi_context`: framework, browser, `environment=ci`, `platform=linux`, build = commit).
Allure: copied only `*-result.json` files and the `browser`, `environment`, `build.number`
and `git.commit` lines of `environment.properties`; removed steps, attachments,
descriptions and the `host`/`thread` labels. The JUnit copies were cleaned like `results/`
and given framework, environment, build and the Allure run's start time.

## `pipelines/`: whole CI pipeline executions (real CI output)

All test reports of two GitHub Actions runs of
[cypress-typescript-framework](https://github.com/niranjankagri/cypress-typescript-framework)
(TaskBoard), one file per job: `api` (Electron), `ui-chrome`, `ui-firefox`, `ui-edge` and
`component` (Chrome). Cleaned with `tools/sanitize_reports.py` like `formats/`.

| Folder | Pipeline run | What happened |
|---|---|---|
| `cypress-taskboard/2026-10-19_80e331e_39238241112` | scheduled run, 19 Oct | all six jobs succeeded; 147 tests passed |
| `cypress-taskboard/2026-10-16_a15d3c7_38842296207` | push, 16 Oct | cancelled when a newer push started the next run: the Firefox UI job uploaded no report; the other jobs' reports are complete (their tests had finished, they were cancelled in later steps) |

`catalog.toml` holds six **synthetic** requirements (TaskBoard has no written requirements),
linked to the real spec files; `gate.toml` requires all five jobs.
`tests/integration/test_pipeline_samples.py` shows the point of pipeline grouping on these
files: the complete run passes, the cancelled run is incomplete (exit 3) although all 114
results that exist passed, and a gate without pipeline grouping would have passed it.
