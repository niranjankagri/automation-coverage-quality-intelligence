# Importing requirements from CSV

Requirements usually live in an issue tracker or a spreadsheet. `qi requirements import` turns a
CSV export into the catalog format, shows what would change, and writes only when asked.

```bash
qi requirements import export.csv --into requirements.toml --catalog catalog.toml          # preview
qi requirements import export.csv --into requirements.toml --catalog catalog.toml --apply  # write
```

Sample: [`samples/requirements.csv`](../samples/requirements.csv)
([download](https://raw.githubusercontent.com/niranjankagri/automation-coverage-quality-intelligence/main/samples/requirements.csv)),
42 synthetic requirements; the committed [`samples/requirements.toml`](../samples/requirements.toml) is
exactly what the import makes of it (checked by `tests/integration/test_sample_requirements_import.py`).

## File format

UTF-8 (Excel: *CSV UTF-8*; a byte order mark is fine), comma-separated, values with commas in
double quotes, first row = column names (case-insensitive). Blank lines are ignored. Up to 10 MB.

| Column | Required | Values | Becomes |
|---|---|---|---|
| `id` | yes | letters, digits, `.`, `_`, `-`; starts with a letter or digit; unique in the file | requirement id |
| `title` | yes | 1-500 characters | title |
| `description` | no | up to 4,000 characters | description (shown on the dashboard's requirement page) |
| `component` (or `feature`) | no | free text | feature, used for grouping and filters |
| `priority` | no | `p1`-`p4` (`P1` accepted) | priority |
| `criticality` | no | `critical`, `high`, `medium`, `low` (any case) | criticality; `critical` drives the gate rules |
| `risk` | no | `high`, `medium`, `low` | risk |
| `platforms` | no | separated by `;` (e.g. `web;api`) | platforms |

An empty cell means "not given"; the requirement then shows as `unspecified` in reports, nothing is
guessed.

## How it fits into the catalog

The import never edits a hand-written file. It writes a **generated** requirements file (first
line `# Generated by qi requirements import`), and the hand-written catalog includes it:

```toml
# catalog.toml (hand-written)
include = ["requirements.toml"]

[[test_case]]
id = "TC-SHOP-CHECKOUT"
requirements = ["SHOP-006"]        # links stay here, untouched by any import
...
```

So the **requirement-to-test mappings are preserved** by design: they live on the test cases in
`catalog.toml`, and the import only replaces requirement entries in `requirements.toml`.

## What a run does

1. Reads the CSV. File-level problems (unreadable, not UTF-8, empty, header only, unknown,
   missing or doubled columns) stop the import with the file name and the reason.
2. Validates every row. Each problem is reported as `row N, column: reason`, where N is the line
   number a spreadsheet shows (the header is row 1):

   ```
   qi: error: export.csv: row 4, title: is required
   qi: error: export.csv: row 5, criticality: Input should be 'critical', 'high', 'medium' or 'low'
   qi: error: export.csv: row 7, id: R-1 is already used in row 2
   qi: error: export.csv: row 9: has 5 values, the header has 4 columns
   ```

3. Compares with the target file by id and prints the plan: **new**, **changed** (with the names of
   the changed fields), **unchanged**, and **kept** (in the target but not in the file).
4. With `--catalog`, checks that no imported id is already defined elsewhere in the catalog (that
   would be a duplicate).
5. Without `--apply`: stops here (preview). With `--apply`: writes the target (existing order kept,
   changed entries updated in place, new ones appended), then loads the whole catalog; if it no
   longer loads (for example a test case links a requirement the new file lacks), the previous file
   is restored and the reason is printed.

**All or nothing:** one invalid row or one conflict means nothing is written.

| Exit code | Meaning |
|---|---|
| 0 | preview shown, or file written (or already up to date) and the catalog loads |
| 2 | `--into` points at a hand-written file (one without the generated marker): refused |
| 3 | the file or a row is invalid, an id conflicts, or the catalog would break: nothing changed |

## Re-importing

Importing the same file again reports every requirement as unchanged and does not even rewrite
the target; records are matched by id, so they are never duplicated. A requirement removed from
the export is **kept** and listed: removing it could break test-case links, so that stays a
decision for a person (delete it from the target by editing the CSV source of truth and checking
the links).

## Not supported (yet)

- Direct connection to a tracker (Jira, Azure DevOps, TargetProcess): export to CSV first.
- Hierarchies (epics, parent requirements) and custom fields: extra columns are refused rather
  than silently dropped, so nothing is lost without notice.
